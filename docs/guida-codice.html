2Il problema e l'idea centrale

Un'azienda riceve fatture che dovrebbero rispettare un contratto quadro (MSA): tariffe massime per servizio, termini di pagamento, regole di adeguamento. La verifica manuale è lenta e campionaria, gli scostamenti (tariffa sopra il massimale, totali riga errati, subtotali incoerenti, termini più restrittivi) diventano sovrafatturazione pagata per errore.

L'idea centrale del progetto è la separazione dei compiti:

  • L'LLM fa ciò che sa fare: leggere testo non strutturato (PDF) e restituirlo in forma strutturata (JSON conforme a uno schema).
  • Python fa ciò che sa fare: moltiplicazioni, somme e confronti al centesimo, senza allucinazioni.
  • L'LLM torna in gioco solo per la parte interpretativa: una discrepanza numerica è coperta da qualche clausola (es. adeguamento ISTAT comunicato) oppure è una violazione?
Regola d'oro. Mai chiedere all'LLM di calcolare. Estrae, Python verifica, l'LLM interpreta. Ogni anomalia architetturale del progetto discende da questa regola.

4Esempio guidato: la fattura INV-2024-1042

Tutto il manuale ragiona su un unico caso, quello delle fixture di test (backend/tests/fixtures/). Fattura INV-2024-1042 di TechConsult S.r.l. contro contratto MSA-2023-ACME-001. Tieni questi numeri a mente: ogni sezione li richiama.

Righe fattura vs massimali

Voce Qty × prezzo Totale esposto Max contratto Esito
Consulenza Senior 10 × 600,00 = 6.000,00 6.000,00 500,00 Tariffa oltre il max: (600 − 500) × 10 = 1.000,00
Sviluppo Software 15 × 450,00 = 6.750,00 6.750,00 450,00 Conforme
Project Management 5 × 550,00 = 2.750,00 2.750,00 550,00 Conforme
Formazione Team 3 × 400,00 = 1.200,00 1.250,00 400,00 (mock) Errore riga: +50,00

Totali e termini

  • Somma righe esposte: 6.000 + 6.750 + 2.750 + 1.250 = 16.750,00. Subtotale dichiarato 16.800,00 → discrepanza subtotale +50,00.
  • Totale: 16.800 + 3.696 (IVA) = 20.496 = totale dichiarato → nessuna discrepanza sul totale (l'errore del subtotale si propaga in modo coerente: ottimo esempio di perché servono controlli separati).
  • Pagamento: fattura 30 giorni contro 60 a contratto → discrepanza termini, senza delta monetario.
  • Totale recuperabile: 1.000 + 50 + 50 = 1.100,00 oltre IVA.
Le 4 discrepanze attese. unit_price:Consulenza Senior (1.000, severità high), line_total:Formazione Team (50, low), subtotal (50, low), payment_terms_days (nessun delta, medium). Il Mock le restituisce tutte come UNJUSTIFIED.

6Modelli Pydantic

backend/models/schemas.py: 8 modelli

Pydantic valida a runtime: se l'LLM restituisce un campo del tipo sbagliato, la validazione fallisce invece di propagare dati sporchi. I vincoli usati qui sono Literal (valori ammessi), default, default_factory e un model_validator cross-field.

Perché le description contano

Ogni Field(description="...") finisce nel JSON Schema inviato all'LLM come response_schema. Esempio di come il modello vede il campo severità: 

{
  "severity": {
    "type": "string",
    "enum": ["low", "medium", "high"],
    "description": "'low' = <5% o <500EUR; ..."
  }
}

La descrizione è contemporaneamente documentazione per lo sviluppatore e istruzione per il modello: scrivere buone description è la forma principale di prompt engineering del progetto.

I modelli in breve

  • InvoiceLine: description, quantity, unit_price, total_price.
  • Invoice: testata (id, vendor, client, date, currency), lines, subtotal, tax_rate/amount, total_amount, payment_terms_days, notes.
  • ContractPricingRule: service_type, max_unit_price, unit, notes.
  • ContractTerms: validita, termini di pagamento, pricing_rules, flag e regole di adeguamento, penali, legge applicabile.
  • Discrepancy: field_name, invoice_value, expected_value, delta, severity, is_justified_by_contract, reasoning.
  • FinalReport: status, id fattura/contratto, summary, discrepancies, total_overbilling, dispute_email_draft.
  • DiscrepancyReasoning / ContractReasoningOutput: schemi intermedi del nodo di reasoning (verdetto JUSTIFIED/UNJUSTIFIED per campo).
  • DisputeEmailDraft: subject + body della bozza.

Il validatore di coerenza

@model_validator(mode="after")
def validate_consistency(self) -> FinalReport:
    if self.status == "DISCREPANCIES_FOUND" and not self.discrepancies:
        raise ValueError("DISCREPANCIES_FOUND richiede almeno una discrepanza.")
    if self.status == "APPROVED" and self.discrepancies:
        raise ValueError("APPROVED non puo contenere discrepanze.")

mode="after" significa: esegui dopo la validazione dei singoli campi, quando l'oggetto e completo. Impedisce di costruire report logicamente contraddittori, da qualunque nodo provengano.

7Stato del grafo

backend/graph/state.py

LangGraph fa circolare un dizionario condiviso tra i nodi. TypedDict(total=False) rende tutte le chiavi facoltative: ogni nodo restituisce solo il delta (le chiavi che aggiorna) e LangGraph lo fonde nello stato globale. A runtime è un normale dict; i tipi servono a IDE e type checker.

class GraphState(TypedDict, total=False):
    invoice_pdf_bytes: bytes
    contract_pdf_bytes: bytes
    raw_invoice_text: str
    raw_contract_text: str
    parsed_invoice: Invoice | None
    parsed_contract: ContractTerms | None
    invoice_extraction_error: str | None
    contract_extraction_error: str | None
    raw_discrepancies: list[Discrepancy]
    analyzed_discrepancies: list[Discrepancy]
    final_report: FinalReport | None

Leggi i campi in ordine di scrittura: input bytes → testi grezzi → oggetti parsati (o errori) → discrepanze grezze → discrepanze analizzate → report. È la cronologia dell'esecuzione.

8Parser PDF

backend/services/pdf_parser.py: extract_text_from_pdf(pdf_bytes, label)

Tre decisioni in una funzione: niente disco (io.BytesIO avvolge i bytes ed espone un'interfaccia file-like a pdfplumber), tolleranze spaziali (x_tolerance=3, y_tolerance=3) per tenere unite parole e celle delle tabelle, separatori --- Pagina N --- così l'LLM sa dove si trova.

with pdfplumber.open(io.BytesIO(pdf_bytes)) as pdf:
    for i, page in enumerate(pdf.pages, 1):
        text = page.extract_text(x_tolerance=3, y_tolerance=3)
        if text:
            pages.append(f"--- Pagina {i} ---\n{text.strip()}")

Pagine-immagine (scansioni) producono warning e, se nessuna pagina ha testo, ValueError: il sistema rifiuta scansioni non OCRizzate invece di inventare dati. I bytes vuoti sono rifiutati subito. Questo è il livello privacy: i PDF vivono solo in RAM e la memoria è rilasciata a fine risposta.

9LLM provider

backend/services/llm_provider.py

L'interfaccia

class BaseLLMProvider(ABC):
    @abstractmethod
    async def structured_completion(
        self, system_prompt: str, user_message: str, output_schema: type[T]
    ) -> T: ...

Una classe astratta con un solo metodo: dato un prompt e uno schema Pydantic, restituisce un'istanza validata di quello schema. I nodi conoscono solo questa interfaccia: nessun import di SDK nei nodi, nessun riferimento a vendor.

L'implementazione Gemini

response = await self._client.aio.models.generate_content(
    model=self._model,
    contents=f"{system_prompt}\n\n{user_message}",
    config={
        "response_mime_type": "application/json",
        "response_schema": output_schema,
        "temperature": 0.1,
    },
)
result = response.parsed  # istanza Pydantic gia validata dall'SDK

Da notare: niente parsing manuale di JSON e niente LangChain in mezzo: lo SDK google-genai vincola l'output allo schema e lo restituisce in response.parsed. Se e None, errore esplicito. Temperature 0.1 per output analitici e stabili. Gli errori di rete/SDK sono incapsulati in LLMProviderError con chaining (raise ... from e).

La factory

create_llm_provider() ricarica .env a ogni chiamata (cambio chiave senza riavvio), restituisce GeminiProvider se la chiave è reale, altrimenti MockLLMProvider con warning. Nei nodi, _get_llm() preferisce il provider iniettato dai test via set_llm_provider().

10Mock provider

backend/services/mock_provider.py

Seleziona la risposta in base a output_schema e restituisce gli oggetti fissi dell'esempio guidato: fattura con le 4 righe note, contratto con le regole e gli adeguamenti ISTAT, 4 reasoning UNJUSTIFIED, bozza email completa. Con should_fail=True solleva sempre LLMProviderError.

A cosa serve: test e CI senza rete né chiavi, demo offline, e, punto didattico importante, rende i test deterministici: stesso input, stesso output, sempre. Un test che dipende da un LLM reale non è un test, è una lotteria.

11Prompt

backend/graph/prompts.py: 4 system prompt

  • EXTRACT_INVOICE_SYSTEM: estrai ogni riga, date YYYY-MM-DD, valuta ISO 4217, valori esatti, non calcolare né inferire.
  • EXTRACT_CONTRACT_SYSTEM: tutte le regole pricing, max come massimale (non sconti), flag ISTAT con condizioni, pagamenti in giorni, null se assente.
  • LLM_REASONING_SYSTEM: per ogni discrepanza JUSTIFIED solo con clausola esplicita, altrimenti UNJUSTIFIED; conservativo nel dubbio; field_name identico all'input (il merge nel nodo 5 si basa su questa uguaglianza).
  • GENERATE_DISPUTE_EMAIL_SYSTEM: oggetto breve, tono assertivo non aggressivo, elenco anomalie, totale, nota di credito entro 15 giorni, riferimento al contratto.
Dettaglio critico. La regola "field_name identico" non è cosmetica: llm_contract_reasoning unisce verdetti e discrepanze con una mappa su field_name. Se l'LLM lo alterasse, il verdetto andrebbe perso e la discrepanza resterebbe ingiustificata di default (fallback conservativo).

12Nodi, controlli e severità

backend/graph/nodes.py: 6 funzioni async/sync

parse_documents, extract_invoice, extract_contract

Parsing locale poi due estrazioni LLM indipendenti. Su LLMProviderError il nodo non solleva: scrive invoice_extraction_error / contract_extraction_error nello stato e il grafo continua verso un report di errore gestito (vedi sezione 19).

deterministic_match: i 5 controlli

  1. Riga: round(qty × unit_price, 2) vs total_price, tolleranza 0.01. Esempio: 3 × 400 = 1.200 vs 1.250 → delta +50.
  2. Subtotale: somma dei totali riga vs subtotale. Esempio: 16.750 vs 16.800 → +50.
  3. Totale: subtotale + IVA vs totale (solo se tax_amount presente). Nell'esempio non scatta.
  4. Tariffe: per ogni riga, cerca la regola con affinità ≥ 0.4 e confronta unit_price > max_unit_price. Esempio: 600 > 500 → sovrapprezzo (600 − 500) × 10 = 1.000.
  5. Termini: se i giorni in fattura sono inferiori a quelli a contratto. Esempio: 30 < 60, delta None, severità fissa medium.

Come funziona il matching tra voce e regola

def _match_service_score(invoice_desc, contract_service):
    a, b = normalizza le due stringhe
    if a == b: return 1.0
    if b in a or a in b: return 0.8
    return |parole in comune| / max(|parole a|, |parole b|)

Tre livelli: uguaglianza, contenimento, overlap lessicale (Jaccard sul massimo, più severo della media). Esempio ipotetico: "Consulenza Junior" vs "Consulenza Senior" → parole {consulenza, junior} e {consulenza, senior} → 1/2 = 0.5, sopra la soglia 0.4: match. La soglia è un compromesso tra tolleranza alle varianti di dicitura e falsi positivi.

Severità

high:   delta > 2000 EUR oppure scostamento > 15%
medium: delta > 500 EUR oppure scostamento > 5%
low:    il resto

Verifica sull'esempio: tariffa 1.000 su riferimento 500 → 200% → high; riga 50 su 1.200 → 4,2% → low; subtotale 50 su 16.750 → 0,3% → low; termini → medium fisso. Il riferimento percentuale è l'importo di confronto (massimale, totale atteso), non il totale fattura.

llm_contract_reasoning e generate_dispute_report

Il reasoning invia discrepanze + contratto serializzato (model_dump_json) e fonde i verdetti con model_copy(update=...): gli oggetti originali non sono mutati. Su errore LLM, fallback conservativo (tutto resta ingiustificato). Il report somma solo i delta positivi ingiustificati (1.000 + 50 + 50 = 1.100; i termini non hanno delta) e chiama l'LLM per l'email solo se ci sono contestazioni, altrimenti dispute_email_draft resta None.

13Grafo e routing

backend/graph/workflow.py

LangGraph modella il flusso come macchina a stati: nodi registrati, edge fissi, un edge condizionale. build_workflow() compila una volta all'avvio; l'oggetto compilato espone ainvoke (batch: aspetta la fine) e astream(stream_mode="updates") (un chunk per nodo completato, usato dallo streaming SSE). 

graph.set_entry_point("parse_documents")
graph.add_edge("parse_documents", "extract_invoice")
graph.add_edge("extract_invoice", "extract_contract")
graph.add_edge("extract_contract", "deterministic_match")
graph.add_conditional_edges("deterministic_match", _route_after_match, {
    "llm_contract_reasoning": "llm_contract_reasoning",
    "generate_dispute_report": "generate_dispute_report",
})
graph.add_edge("llm_contract_reasoning", "generate_dispute_report")
graph.add_edge("generate_dispute_report", END)

Il router è una funzione pura sullo stato: se raw_discrepancies e non vuota → reasoning, altrimenti report diretto. Fattura conforme = zero token di reasoning. Nota didattica: le due estrazioni LLM sono sequenziali nel grafo; parallelizzarle è una possibile ottimizzazione (sono indipendenti), a costo di maggiore complessità di gestione errori.

Il protocollo SSE

/analyze/stream restituisce StreamingResponse con un generatore asincrono: ogni yield "data: {...}\n\n" è un flush verso il browser, senza aspettare la fine del grafo. Sequenza tipica: 

data: {"type": "init", "message": "Avvio analisi..."}
data: {"type": "node_update", "node": "parse_documents", "elapsed": 0.03, "summary": "PDF estratti: ..."}
data: {"type": "node_update", "node": "extract_invoice", ...}
...
data: {"type": "complete", "report": {...}, "elapsed": 32.5}

Il riepilogo per nodo è costruito dal server ispezionando il delta di stato (stessa logica del CLI). Errori di upload: 400 per content-type non PDF o file vuoto. Errori di workflow: 500. Le fixture mancanti sono rigenerate al volo da generate_test_pdfs. Il frontend è servito su /, questa guida su /docs.

Strategia: perché questi test funzionano

  • Fixture con anomalie note (generate_test_pdfs.py, fpdf2): i PDF non sono casuali, contengono esattamente le 4 discrepanze della sezione 4. Se il sistema ne trova 3 o 5, qualcosa si è rotto.
  • Mock deterministico: i test di workflow e API iniettano MockLLMProvider via set_llm_provider() e lo resettano dopo ogni test (fixture autouse). Nessuna rete, nessuna chiave, esecuzione sotto il secondo.
  • Tre livelli: unita (parser, match), integrazione (grafo), API (TestClient in-process, senza socket reali).
  • Asserzioni sui numeri, non sulle parole: delta == 1000.0, total_overbilling >= 1000.0. I testi LLM non sono mai assertati alla lettera (sarebbero fragili anche con il Mock, e impossibili con un modello reale).

17Frontend in dettaglio

frontend/index.html · frontend/css/style.css · frontend/js/app.js

Struttura della pagina

  • Topbar: brand, badge stato API (/health), badge modalità LLM (/demo-fixtures/status), link a questa guida.
  • Sezione 1, input: due dropzone (click, tastiera, drag and drop) con validazione PDF e limite 10 MB, anteprima nome/dimensione, rimozione, pulsante demo e avvio (abilitato solo con entrambi i file).
  • Sezione 2, avanzamento: stepper a 5 fasi (parsing, estrazione, confronto, valutazione, report) più log SSE con timer.
  • Sezione 3, risultati: banner esito, KPI (importo contestabile, id fattura/contratto, conteggio, durata), tabella discrepanze con filtri per severità, bozza email con copia negli appunti, pulsante nuova analisi.

Macchina a stati del client

startAnalysis() segue un ciclo fisso: valida → congela i pulsanti → mostra stepper e azzera log → apre fetch("/analyze/stream") → legge il reader chunk per chunk, accumula il buffer, spezza su \n\n, parsifica ogni riga data: → aggiorna stepper (nodeToStep) e log → su complete memorizza il report → nasconde lo stepper e renderizza. Errori di rete o eventi error mostrano un toast e ripristinano i pulsanti. Il mapping nodi→step comprime le due estrazioni in un unico step "Estrazione dati".

Stile

Tema chiaro con token condivisi con questa guida (--bg, --surface, --accent, font di sistema). Nessuna dipendenza esterna: un HTML, un CSS, un JS vanilla.

18Estendere il sistema: tre ricette

A. Aggiungere un controllo deterministico

Apri deterministic_match in nodes.py e appendi una Discrepancy con field_name univoco (diventera chiave del reasoning e dei test). Esempio di scheletro: 

if invoice.due_date is not None and ...:
    discrepancies.append(Discrepancy(
        field_name="due_date",
        invoice_value=...,
        expected_value=...,
        delta=None,
        severity="low",
        is_justified_by_contract=False,
        reasoning="...",
    ))

Poi aggiungi il caso in test_deterministic_match.py e, se serve, il verdetto atteso nel Mock.

B. Aggiungere un provider LLM

  1. Crea una sottoclasse di BaseLLMProvider che implementa structured_completion (chiamata API + validazione output_schema).
  2. Aggiungi il ramo in create_llm_provider() letto da una nuova variabile d'ambiente.
  3. Verifica con la suite esistente: i test usano il Mock e devono restare verdi senza toccarli.

C. Aggiungere un endpoint

Segui il pattern di /analyze: valida l'upload con _read_pdf_upload, invoca il workflow, gestisci 400/500. Per output progressivi, copia il generatore di /analyze/stream e aggiungi i tipi di evento che servono al client.

19Gestione degli errori

Guasto Dove Comportamento
File non PDF / vuoto main._read_pdf_upload HTTP 400 con dettaglio
PDF senza testo (scansione) pdf_parser ValueError → 500 via workflow, messaggio esplicito
Estrazione LLM fallita extract_* Errore nello stato, grafo non collassa
Reasoning LLM fallito llm_contract_reasoning Fallback: discrepanze restano ingiustificate
Email LLM fallita generate_dispute_report Segnaposto testuale, report comunque valido
Estrazione fallita a monte generate_dispute_report Report APPROVED con summary "Analisi incompleta..." e zero discrepanze
Report mancante in stream analyze_stream Evento error al client
Scelta di design. A estrazione fallita il report e APPROVED con zero discrepanze: il validatore lo impone. Il summary spiega l'incompletezza, ma un consumatore che guarda solo status potrebbe fraintendere. Se integri via API, controlla sempre analysis_summary.
