2The problem and the core idea

A company receives invoices that should comply with a framework contract (MSA): maximum rates per service, payment terms, adjustment rules. Manual verification is slow and sample-based; deviations: rates above the cap, wrong line totals, inconsistent subtotals, stricter terms, become overbilling paid by mistake.

The core idea of the project is the separation of concerns:

  • The LLM does what it is good at: reading unstructured text (PDFs) and returning it in structured form (JSON conforming to a schema).
  • Python does what it is good at: multiplications, sums and comparisons to the cent, with no hallucinations.
  • The LLM comes back into play only for the interpretive part: is a numeric discrepancy covered by some clause (e.g. a notified ISTAT adjustment) or is it a violation?
Golden rule. Never ask the LLM to compute. It extracts, Python verifies, the LLM interprets. Every architectural choice in the project follows from this rule.

4Worked example: invoice INV-2024-1042

The whole manual reasons about a single case, the test fixtures (backend/tests/fixtures/). Invoice INV-2024-1042 from TechConsult S.r.l. against contract MSA-2023-ACME-001. Keep these numbers in mind: every section refers back to them.

Invoice lines vs caps

Consulenza Senior10 × 600.00 = 6,000.006,000.00500.00Rate above cap: (600 − 500) × 10 = 1,000.00

Totals and terms

  • Sum of stated lines: 6,000 + 6,750 + 2,750 + 1,250 = 16,750.00; stated subtotal 16,800.00 → subtotal discrepancy +50.00.
  • Total: 16,800 + 3,696 (VAT) = 20,496 = stated total → no total discrepancy (the subtotal error propagates consistently: a good example of why separate checks are needed).
  • Payment: invoice 30 days vs 60 under contract → terms discrepancy, with no monetary delta.
  • Recoverable total: 1,000 + 50 + 50 = 1,100.00 plus VAT.
The 4 expected discrepancies. unit_price:Consulenza Senior (1,000, high severity), line_total:Formazione Team (50, low), subtotal (50, low), payment_terms_days (no delta, medium). The Mock returns all of them as UNJUSTIFIED.

6Pydantic models

backend/models/schemas.py: 8 models

Pydantic validates at runtime: if the LLM returns a wrongly typed field, validation fails instead of propagating dirty data. The constraints used here are Literal (allowed values), defaults, default_factory and a cross-field model_validator.

Why descriptions matter

Every Field(description="...") ends up in the JSON Schema sent to the LLM as response_schema. Example of how the model sees the severity field:

{
  "severity": {
    "type": "string",
    "enum": ["low", "medium", "high"],
    "description": "'low' = <5% o <500EUR; ..."
  }
}

The description is both developer documentation and model instruction: writing good descriptions is the main form of prompt engineering in this project.

The models in brief

  • InvoiceLine: description, quantity, unit_price, total_price.
  • Invoice: header (id, vendor, client, dates, currency), lines, subtotal, tax rate/amount, total, payment terms, notes.
  • ContractPricingRule: service_type, max_unit_price, unit, notes.
  • ContractTerms: validity, payment terms, pricing rules, adjustment flag and rules, penalties, governing law.
  • Discrepancy: field_name, invoice_value, expected_value, delta, severity, is_justified_by_contract, reasoning.
  • FinalReport: status, invoice/contract ids, summary, discrepancies, total_overbilling, dispute_email_draft.
  • DiscrepancyReasoning / ContractReasoningOutput: intermediate reasoning-node schemas (JUSTIFIED/UNJUSTIFIED verdict per field).
  • DisputeEmailDraft: subject + body of the draft.

The consistency validator

@model_validator(mode="after")
def validate_consistency(self) -> FinalReport:
    if self.status == "DISCREPANCIES_FOUND" and not self.discrepancies:
        raise ValueError("DISCREPANCIES_FOUND richiede almeno una discrepanza.")
    if self.status == "APPROVED" and self.discrepancies:
        raise ValueError("APPROVED non puo contenere discrepanze.")

mode="after" means: run after single-field validation, when the object is complete. It prevents building logically contradictory reports, regardless of which node produced them. (String literals are shown verbatim as in the source.)

7Graph state

backend/graph/state.py

LangGraph circulates a shared dictionary between nodes. TypedDict(total=False) makes all keys optional: each node returns only the delta (the keys it updates) and LangGraph merges it into the global state. At runtime it is a plain dict; the types serve the IDE and the type checker.

class GraphState(TypedDict, total=False):
    invoice_pdf_bytes: bytes
    contract_pdf_bytes: bytes
    raw_invoice_text: str
    raw_contract_text: str
    parsed_invoice: Invoice | None
    parsed_contract: ContractTerms | None
    invoice_extraction_error: str | None
    contract_extraction_error: str | None
    raw_discrepancies: list[Discrepancy]
    analyzed_discrepancies: list[Discrepancy]
    final_report: FinalReport | None

Read the fields in write order: input bytes → raw texts → parsed objects (or errors) → raw discrepancies → analyzed discrepancies → report. That is the execution timeline.

8PDF parser

backend/services/pdf_parser.py: extract_text_from_pdf(pdf_bytes, label)

Three decisions in one function: no disk (io.BytesIO wraps the bytes and exposes a file-like interface to pdfplumber), spatial tolerances (x_tolerance=3, y_tolerance=3) to keep table words and cells together, --- Pagina N --- separators so the LLM knows where it is. (Page markers use the source language.)

with pdfplumber.open(io.BytesIO(pdf_bytes)) as pdf:
    for i, page in enumerate(pdf.pages, 1):
        text = page.extract_text(x_tolerance=3, y_tolerance=3)
        if text:
            pages.append(f"--- Pagina {i} ---\n{text.strip()}")

Image-only pages (scans) produce warnings and, if no page has extractable text, ValueError: the system rejects non-OCRed scans instead of inventing data. Empty bytes are rejected immediately. This is the privacy layer: PDFs live only in RAM and memory is released at the end of the response.

9LLM provider

backend/services/llm_provider.py

The interface

class BaseLLMProvider(ABC):
    @abstractmethod
    async def structured_completion(
        self, system_prompt: str, user_message: str, output_schema: type[T]
    ) -> T: ...

An abstract class with a single method: given a prompt and a Pydantic schema, return a validated instance of that schema. Nodes only know this interface: no SDK imports in the nodes, no vendor references.

The Gemini implementation

response = await self._client.aio.models.generate_content(
    model=self._model,
    contents=f"{system_prompt}\n\n{user_message}",
    config={
        "response_mime_type": "application/json",
        "response_schema": output_schema,
        "temperature": 0.1,
    },
)
result = response.parsed  # Pydantic instance already validated by the SDK

Note: no manual JSON parsing and no LangChain in between: the google-genai SDK constrains the output to the schema and returns it in response.parsed. If it is None, explicit error. Temperature 0.1 for stable, analytical output. Network/SDK errors are wrapped in LLMProviderError with chaining (raise ... from e).

The factory

create_llm_provider() reloads .env on every call (key changes without restart), returns GeminiProvider when the key is real, otherwise MockLLMProvider with a warning. In the nodes, _get_llm() prefers the test-injected provider via set_llm_provider().

10Mock provider

backend/services/mock_provider.py

Selects the response by output_schema and returns the fixed objects of the worked example: invoice with the 4 known lines, contract with rules and ISTAT adjustments, 4 UNJUSTIFIED reasonings, complete email draft. With should_fail=True it always raises LLMProviderError.

Its purpose: keyless, network-free tests and CI, offline demos, and, the important teaching point, it makes tests deterministic: same input, same output, always. A test depending on a live LLM is not a test, it is a lottery.

11Prompts

backend/graph/prompts.py: 4 system prompts (Italian source text, shown here translated)

  • EXTRACT_INVOICE_SYSTEM: extract every line, YYYY-MM-DD dates, ISO 4217 currency, exact values, do not compute or infer.
  • EXTRACT_CONTRACT_SYSTEM: all pricing rules, cap as maximum (not discounts), ISTAT flag with conditions, payments in days, null when absent.
  • LLM_REASONING_SYSTEM: per discrepancy, JUSTIFIED only with an explicit clause, otherwise UNJUSTIFIED; conservative on doubt; field_name identical to the input (the merge in node 5 relies on this equality).
  • GENERATE_DISPUTE_EMAIL_SYSTEM: short subject, assertive non-aggressive tone, list of anomalies, total, credit note within 15 days, contract reference.
Critical detail. The "identical field_name" rule is not cosmetic: llm_contract_reasoning joins verdicts and discrepancies through a field_name map. If the LLM altered it, the verdict would be lost and the discrepancy would stay unjustified by default (conservative fallback).

12Nodes, checks and severity

backend/graph/nodes.py: 6 sync/async functions

parse_documents, extract_invoice, extract_contract

Local parsing, then two independent LLM extractions. On LLMProviderError the node does not raise: it writes invoice_extraction_error / contract_extraction_error into the state and the graph continues toward a handled error report (see section 19).

deterministic_match: the 5 checks

  1. Line: round(qty × unit_price, 2) vs total_price, tolerance 0.01. Example: 3 × 400 = 1,200 vs 1,250 → delta +50.
  2. Subtotal: sum of line totals vs subtotal. Example: 16,750 vs 16,800 → +50.
  3. Total: subtotal + VAT vs total (only when tax_amount is present). Does not trigger in the example.
  4. Rates: per line, find the rule with affinity ≥ 0.4 and compare unit_price > max_unit_price. Example: 600 > 500 → overcharge (600 − 500) × 10 = 1,000.
  5. Terms: invoice days below contract days. Example: 30 < 60, delta None, fixed medium severity.

How line-to-rule matching works

def _match_service_score(invoice_desc, contract_service):
    a, b = normalized strings
    if a == b: return 1.0
    if b in a or a in b: return 0.8
    return |shared words| / max(|words a|, |words b|)

Three levels: equality, containment, lexical overlap (Jaccard over the maximum, stricter than the average). Hypothetical example: "Consulenza Junior" vs "Consulenza Senior" → words {consulenza, junior} and {consulenza, senior} → 1/2 = 0.5, above the 0.4 threshold: match. The threshold trades tolerance for label variants against false positives.

Severity

high:   delta > 2000 EUR or deviation > 15%
medium: delta > 500 EUR or deviation > 5%
low:    the rest

Check on the example: rate 1,000 over reference 500 → 200% → high; line 50 over 1,200 → 4.2% → low; subtotal 50 over 16,750 → 0.3% → low; terms → fixed medium. The percentage reference is the comparison amount (cap, expected total), not the invoice total.

llm_contract_reasoning and generate_dispute_report

Reasoning sends discrepancies + serialized contract (model_dump_json) and merges verdicts with model_copy(update=...): original objects are never mutated. On LLM error, conservative fallback (everything stays unjustified). The report sums only positive unjustified deltas (1,000 + 50 + 50 = 1,100; terms have no delta) and calls the LLM for the email only when there are disputes, otherwise dispute_email_draft stays None.

13Graph and routing

backend/graph/workflow.py

LangGraph models the flow as a state machine: registered nodes, fixed edges, one conditional edge. build_workflow() compiles once at startup; the compiled object exposes ainvoke (batch: waits for completion) and astream(stream_mode="updates") (one chunk per completed node, used by SSE streaming).

graph.set_entry_point("parse_documents")
graph.add_edge("parse_documents", "extract_invoice")
graph.add_edge("extract_invoice", "extract_contract")
graph.add_edge("extract_contract", "deterministic_match")
graph.add_conditional_edges("deterministic_match", _route_after_match, {
    "llm_contract_reasoning": "llm_contract_reasoning",
    "generate_dispute_report": "generate_dispute_report",
})
graph.add_edge("llm_contract_reasoning", "generate_dispute_report")
graph.add_edge("generate_dispute_report", END)

The router is a pure function of the state: if raw_discrepancies is non-empty → reasoning, otherwise straight to the report. A compliant invoice costs zero reasoning tokens. Teaching note: the two LLM extractions are sequential in the graph; parallelizing them is a possible optimization (they are independent), at the cost of more complex error handling.

The SSE protocol

/analyze/stream returns a StreamingResponse with an async generator: each yield "data: {...}\n\n" flushes to the browser without waiting for the graph to finish. Typical sequence:

data: {"type": "init", "message": "Avvio analisi..."}
data: {"type": "node_update", "node": "parse_documents", "elapsed": 0.03, "summary": "PDF estratti: ..."}
data: {"type": "node_update", "node": "extract_invoice", ...}
...
data: {"type": "complete", "report": {...}, "elapsed": 32.5}

(Init message and summaries use the source language.) The per-node summary is built server-side by inspecting the state delta (same logic as the CLI). Upload errors: 400 for non-PDF content type or empty file. Workflow errors: 500. Missing fixtures are regenerated on the fly by generate_test_pdfs. The frontend is served at /, this guide at /docs.

Strategy: why these tests work

  • Fixtures with known anomalies (generate_test_pdfs.py, fpdf2): the PDFs are not random, they contain exactly the 4 discrepancies of section 4. If the system finds 3 or 5, something broke.
  • Deterministic mock: workflow and API tests inject MockLLMProvider via set_llm_provider() and reset it after each test (autouse fixture). No network, no keys, sub-second runs.
  • Three levels: unit (parser, match), integration (graph), API (in-process TestClient, no real sockets).
  • Assertions on numbers, not words: delta == 1000.0, total_overbilling >= 1000.0. LLM texts are never asserted literally (fragile even with the Mock, impossible with a live model).

16CLI runners

backend/run_live_stream.py · backend/tests/run_demo.py

run_live_stream.py consumes workflow.astream(stream_mode="updates") and prints one line per node with timing and summary: the same data source as SSE, useful for debugging without a browser. run_demo.py runs ainvoke and prints the report, discrepancies and email draft. Both regenerate missing fixtures and fall back to the Mock without a Gemini key. Note: run_demo.py imports the Mock from services.mock_provider (direct import, not via other modules).

17Frontend in detail

frontend/index.html · frontend/css/style.css · frontend/js/app.js

Page structure

  • Topbar: brand, API status badge (/health), LLM mode badge (/demo-fixtures/status), link to this guide.
  • Section 1, input: two PDF dropzones (click, keyboard, drag and drop) with PDF validation and a 10 MB limit, name/size preview, removal, demo and start buttons (start enabled only with both files).
  • Section 2, progress: 5-step stepper (parsing, extraction, comparison, evaluation, report) plus SSE log with timer.
  • Section 3, results: outcome banner, KPIs (contestable amount, invoice/contract ids, count, duration), discrepancy table with severity filters, email draft with clipboard copy, new-analysis button.

Client state machine

startAnalysis() follows a fixed cycle: validate → freeze buttons → show stepper and clear log → open fetch("/analyze/stream") → read the reader chunk by chunk, accumulate the buffer, split on \n\n, parse each data: line → update stepper (nodeToStep) and log → on complete store the report → hide the stepper and render. Network errors or error events show a toast and restore the buttons. The node-to-step mapping compresses both extractions into a single "data extraction" step.

Style

Light theme with tokens shared with this guide (--bg, --surface, --accent, system fonts). No external dependencies: one HTML, one CSS, one vanilla JS file. (The UI itself is in Italian.)

18Extending the system: three recipes

A. Add a deterministic check

Open deterministic_match in nodes.py and append a Discrepancy with a unique field_name (it becomes the key for reasoning and tests). Skeleton:

if invoice.due_date is not None and ...:
    discrepancies.append(Discrepancy(
        field_name="due_date",
        invoice_value=...,
        expected_value=...,
        delta=None,
        severity="low",
        is_justified_by_contract=False,
        reasoning="...",
    ))

Then add the case in test_deterministic_match.py and, if needed, the expected verdict in the Mock.

B. Add an LLM provider

  1. Create a BaseLLMProvider subclass implementing structured_completion (API call + output_schema validation).
  2. Add the branch in create_llm_provider() driven by a new environment variable.
  3. Verify with the existing suite: tests use the Mock and must stay green untouched.

C. Add an endpoint

Follow the /analyze pattern: validate the upload with _read_pdf_upload, invoke the workflow, handle 400/500. For progressive output, copy the /analyze/stream generator and add the event types the client needs.

Design choice. On failed extraction the report is APPROVED with zero discrepancies: the validator requires it. The summary explains the incompleteness, but a consumer looking only at status could misunderstand. When integrating via API, always check analysis_summary.
